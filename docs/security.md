# Проверка доступа перед включением записи

Исходный API принимал операции записи без проверки владельца и логировал целые объекты фильмов с заметками. Старый браузерный код содержал ключ Кинопоиска и вставлял заметки в HTML без экранирования. Ключ поиска нужно заменить у провайдера. Публичный ключ Supabase из старой истории сам по себе не даёт административных прав. Его возможности определяют права ролей и RLS. Изменения в этой ветке не отзывают ключи из истории Git.

Исходные страницы и API находились во вложенной папке. Конфигурация vercel..json не распознавалась, универсальный маршрут стоял перед маршрутом API. В проекте с type=module сервер использовал require. Скрипт карточки ссылался на отсутствующие функции, часть рейтингов и повторно объявленная функция удаления обращались к localStorage. При выводе фильмов сортировка по дате переворачивалась вставкой в начало списка. Новая версия использует один серверный источник, отдельные маршруты и одинаковый формат модулей. Существующий localStorage браузеров не очищается и не импортируется автоматически.

Откройте **отдельный тестовый проект**. В SQL Editor выполните [rls-audit.sql](rls-audit.sql). Файл использует только SELECT в read-only транзакции. Сравните имена и типы колонок с server/data.mjs. Для установки функции проверьте совместимость ID с bigint, типов заметок с text, флага с boolean. Для идемпотентной вставки требуется первичный ключ или UNIQUE по id.

| Операция над public.movies | anon | authenticated, посторонний UUID | authenticated, один из двух владельцев |
| --- | --- | --- | --- |
| SELECT | Только записи, открытые владельцами для публичной коллекции | Согласно политике чтения | Все записи владельцев |
| INSERT | Запрещено | Запрещено политикой WITH CHECK | Разрешено для добавления |
| UPDATE | Запрещено | Запрещено политикой USING / WITH CHECK | Только user_notes, girlfriend_notes, has_spoilers |
| DELETE, TRUNCATE | Запрещено | Запрещено | Запрещено |

Включите RLS. Политики должны проверять auth.uid() по двум конкретным UUID. Дополнительная permissive policy складывается с уже имеющимися по OR, поэтому широкая старая политика записи продолжит действовать. Проверьте унаследованные права PUBLIC, table-level UPDATE и отдельные column grants. На authenticated нужен UPDATE только трёх указанных колонок, без общего UPDATE на таблицу. Для чтения учитывайте, что исходная публичная коллекция включает обе заметки. Предупреждение о спойлерах управляет показом текста, но не является ограничением доступа.

Установите [notes-function.sql](notes-function.sql) после проверки схемы на staging. Функция имеет SECURITY INVOKER и требует обычные RLS и права колонок. Предыдущие заметки передаются в теле RPC. Несовпадение возвращает пустой результат и API отвечает 409. Установка создаёт только функцию с узкими правами исполнения. Для отката DBA может убрать только эту функцию с указанной в файле сигнатурой. Схема таблицы и существующие записи установки не требуют.

Проверьте матрицу на тестовой базе, включая прямой доступ через Supabase Data API. При действующей широкой политике прежний публичный ключ может обращаться к БД мимо приложения. Флаг RLS_VERIFIED — подтверждение администратора, а не автоматический аудит. Перед согласованными изменениями production сохраните исходные определения политик, grants и резервную копию. Секретный ключ, JSON с заметками и конфигурацию .env не загружайте в GitHub.

Для отката записи переключите ENABLE_WRITES в false и обновите развёртывание. Изменение политик production и выпуск в production выполняются отдельно по решению владельца.
