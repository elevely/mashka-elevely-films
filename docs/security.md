# Права доступа и сохранность данных

Рабочий Supabase в этой сессии не подключался. Текущие политики, схема и полнота backup **не подтверждены**. Проверенная локально схема — синтетическая, с bigint ID, jsonb-наборами оценок, nullable личными/общими итогами и legacy-колонкой. Если настоящая схема отличается (например, запрещает NULL до второй оценки), остановитесь и подготовьте отдельное совместимое изменение после backup и согласования. Не меняйте constraints вслепую.

## Обнаруженное ранее и сейчас

Предыдущая версия API не различала двух зрителей, принимала оценки и заметки обоих, запрещала изменение сохранённых оценок и хранила только часовой access cookie. Теперь сервер определяет автора по двум фиксированным Auth UUID, принимает только собственный набор, использует HttpOnly refresh cookie и атомарную проверку ревизии. Metadata профиля и старый ALLOWED_ADMIN_IDS не назначают роль.

В Git-истории найдены встроенные API-ключи в `mashka-elevely-films/public/script.js` и `mashka-elevely-films/script.js`. **Ключ Кинопоиска нужно отозвать и заменить у провайдера.** История не переписывалась. Публичный anon-ключ Supabase не административный секрет: его доступ ограничивается RLS/grants. Актуальная проверка распространённых шаблонов private keys, GitHub tokens и Supabase secret keys не нашла совпадений в отслеживаемых файлах. Такая проверка не является доказательством отсутствия любых секретов.

## Перед установкой защиты

1. Выберите отдельный тестовый Supabase. В рабочем проекте сначала получите разрешение и проверенную резервную копию; Git-копия недостаточна.
2. Выполните [rls-audit.sql](rls-audit.sql) — только SELECT, без чтения заметок. Сохраните все определения политик, grants, ограничений, триггеров и функций приватно. Проверьте существующие нестандартные триггеры, роли и SECURITY DEFINER RPC: другой RPC с повышенными правами может обойти привычные grants, поэтому его также нужно проверить.
3. Сверьте `id`, `movie_data`, `user_ratings`, `girlfriend_ratings`, `user_total`, `girlfriend_total`, `final_rating`, `date_added`, `user_notes`, `girlfriend_notes`, `has_spoilers` и nullable-ограничения. Для ID нужна уникальность. Не добавляйте индексы, не удаляйте дубли и не меняйте старые строки автоматически.
4. Создайте/используйте двух Auth-пользователей; убедитесь, что UUID различны. Отключите публичную регистрацию. Замените ВСЕ UUID-маркеры в [owner-writes.sql](owner-writes.sql), включая проверку в начале файла. Значения должны совпадать с окружением приложения.
5. Проверьте SQL в staging. Файл применяется один раз, в транзакции; не является универсальной повторяемой миграцией. Существующие объекты с совпавшими именами нужно исследовать, а не удалять автоматически. SQL не обновляет строки фильмов.

## Модель доступа

| Операция | anon | Посторонний authenticated UUID | elevely / Машка |
| --- | --- | --- | --- |
| SELECT | Согласно существующим политикам публичного чтения | Restrictive policy закрывает доступ | Все фильмы |
| INSERT | Запрещён grants | Запрещён RLS и триггером | Свои оценки; второй набор пуст |
| UPDATE | Запрещён grants | Запрещён RLS и триггером | Только свои критерии/заметка, общий флаг спойлеров; итоги вычисляет триггер |
| DELETE / TRUNCATE | Запрещён | Запрещён | Запрещён |
| Изменение ID / даты / metadata / чужой рецензии | Запрещено | Запрещено | Запрещено |

`films_actor()` сопоставляет `auth.uid()` с двумя UUID. Restrictive policy ограничивает старые permissive policies, которые иначе складывались бы по OR. Скрипт отнимает широкие table- и column-grants записи у PUBLIC, anon, authenticated, затем выдаёт узкий список. `films_guard_review` действует и при прямых INSERT/UPDATE через Supabase REST. Он сохраняет неизвестные старые поля, отклоняет чужие изменения и вычисляет итоги только при изменении собственных критериев. Защита от дублей сериализует добавления через transaction advisory lock; старые дубли не удаляются.

`films_update_review` — SECURITY INVOKER с пустым search_path. Она принимает прежний полный JSON строки, блокирует строку и сравнивает её до UPDATE. При конфликте результат пустой, API отвечает 409. Политики, grants и триггер продолжают действовать. Прежняя `films_update_notes` не требуется новой версии; если уже установлена, её тоже ограничивает триггер. Не удаляйте старые функции без инвентаризации клиентов.

Сервисные роли, владельцы таблиц и администраторы PostgreSQL не являются обычными пользователями: они могут менять саму защиту. Привилегированные ключи не должны попадать в приложение. Runtime отклоняет `sb_secret_…` и JWT `service_role` в SUPABASE_ANON_KEY; локальный backup клиент допускает такой ключ только для GET.

## Сессии и веб-защита

- Access и refresh tokens — только HttpOnly, SameSite=Strict cookies, Secure в HTTPS. Frontend не видит токены и не хранит их в localStorage. Refresh идёт через origin-защищённый PUT; внутри вкладки один запрос, между поддерживающими Web Locks вкладками — последовательные запросы.
- Auth проверяется на сервере через Supabase `/auth/v1/user`. Просроченная сессия продлевается, отозванная требует входа. Сетевой сбой не удаляет refresh cookie. Logout отзывает текущую refresh-сессию через `scope=local`. Как и у обычного Supabase JWT, ранее скопированный access token может действовать до его срока окончания; мгновенный отзыв каждого access JWT не реализован.
- Все записи, refresh и logout проверяют точный Origin и Sec-Fetch-Site. Preview fallback использует доверенный VERCEL_URL, не входящий Host. Production требует APP_ORIGIN.
- API разрешает только определённые поля, проверяет диапазоны, лимиты текста, ID и размер JSON 64 KiB. PostgREST-параметры формируются через URLSearchParams; SQL-вставок строк из пользовательского ввода нет.
- CSP ограничивает скрипты собственным origin, запрещает framing, inline scripts и формы на чужие адреса. Названия, заметки и другие динамические строки экранируются. Постеры допускают только HTTPS без credentials, предусмотрен fallback.
- Пароли и cookies не логируются. Ошибки сторонних сервисов заменены безопасными сообщениями; Auth rate limiting остаётся на стороне Supabase.
- Публичное чтение сохранено: гость видит коллекцию **вместе с обеими заметками**, если это разрешено anon RLS. Скрытие спойлера — интерфейсная функция. Для приватной коллекции требуется отдельное согласованное изменение чтения API и RLS.

## Перед включением production-записи

Сверьте полный экспорт до/после установки, проверьте оба аккаунта и анонима, посторонний UUID, прямые чужие записи, удаление, дубли и конкурирующие формы в настоящем staging. Установите `RLS_VERIFIED=true` только по результатам проверки, затем включите ENABLE_WRITES. Оба флага не заменяют защиту БД.

В этой сессии production SQL не запускался, настоящие данные не читались и не изменялись, backup настоящей базы не создавался. Для rollback сначала выключите запись и перевыпустите приложение. Не снимайте триггер только ради восстановления старого интерфейса. Восстановление прав/данных выполняется по приватной резервной копии и отдельному согласию владельца.
